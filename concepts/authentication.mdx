Auth Backend uses a stateless, token-based authentication model built on Spring Security, jjwt 0.12.6, and HttpOnly cookies. This page explains how every incoming request is authenticated, how tokens are issued and expire, how the Google OAuth2 flow works end-to-end, and how local accounts differ from social-login accounts.

## JWT Authentication Filter

Every request passes through `JwtAuthenticationFilter` before it reaches any controller. The filter extracts and validates an access token from one of two places, in this order of precedence:

1. **`Authorization: Bearer <token>` header** — used by mobile apps, API clients, and server-to-server calls.
2. **`access_token` HttpOnly cookie** — set automatically by the browser on every same-origin request.

If both are present, the Bearer header wins and the cookie is ignored.

<Note>
  Because the filter uses `OncePerRequestFilter`, it runs exactly once per request regardless of how many security filter chains are configured.
</Note>

After extracting the raw JWT string the filter validates it in three stages:

<Steps>
  <Step title="Parse and verify signature">
    The token is parsed with `Jwts.parser().verifyWith(signingKey)`. An `HS256` HMAC-SHA256 key derived from the `jwt.secret` property is used. Any tampered or forged token is rejected with `HTTP 401`.
  </Step>
  <Step title="Check required custom claims">
    Every access token must carry four custom claims: `role`, `active`, `uid` (user UUID), and `sid` (session UUID). Tokens that predate this claim set — or tokens generated by another service — are treated as anonymous rather than authenticated.
  </Step>
  <Step title="Validate session in Redis">
    The `sid` claim is looked up in Redis (`SessionRedisRepository`). If the entry is missing — because the session was explicitly revoked, because the refresh token expired, or because `logout-all` was called — the request is treated as unauthenticated. This closes the revocation window to near-real-time rather than waiting for the access token to expire naturally.
  </Step>
</Steps>

If the token is expired or has an invalid signature, the filter writes an `application/problem+json` body and returns `HTTP 401` immediately. If required claims (`role`, `active`, `uid`, `sid`) are missing, the `active` claim is `false`, or the Redis session lookup fails, the request continues as anonymous — Spring Security's `AuthorizationFilter` then rejects it with `HTTP 401` if the endpoint requires authentication.

## Token Lifecycle

Auth Backend issues two distinct JWT tokens per session.

<CardGroup cols={2}>
  <Card title="Access Token" icon="bolt">
    Short-lived credential delivered via the `access_token` HttpOnly cookie. Expiry is controlled by `jwt.time.expiration` (default: `900000` ms = 15 minutes). Carries `role`, `active`, `uid`, and `sid` claims. Must be refreshed before it expires.
  </Card>
  <Card title="Refresh Token" icon="arrows-rotate">
    Long-lived credential stored in the `refresh_token` cookie and persisted (hashed) in PostgreSQL. Expiry is controlled by `jwt.time.refresh-expiration` (default: `604800000` ms = 7 days). Used only at `POST /api/v1/auth/refresh`. Rotated on every use.
  </Card>
</CardGroup>

### Token Rotation

When `POST /api/v1/auth/refresh` is called, Auth Backend:

1. Reads the `refresh_token` cookie.
2. Verifies the JWT signature and checks that the token is not revoked or expired in the database.
3. Issues a **new** refresh token and a **new** access token.
4. Marks the old refresh token as revoked.
5. Updates `lastUsedAt` on the session record.
6. Writes new `access_token` and `refresh_token` cookies via `Set-Cookie`.

The old access token remains valid until its `exp` claim passes (up to 15 minutes), but the Redis entry for the session is updated to track the new refresh token.

## Cookie Configuration

Both tokens travel exclusively as HttpOnly cookies in browser contexts. The relevant application properties are:

```properties application.properties
# Tokens expire based on these values (milliseconds)
jwt.time.expiration=900000
jwt.time.refresh-expiration=604800000

# Cookie security flags — change for production
app.cookie.secure=false
app.cookie.same-site=Lax
```

<Warning>
  In production set `app.cookie.secure=true` so cookies are only sent over HTTPS. Also consider setting `app.cookie.same-site=Strict` if your frontend and API share the same registrable domain to prevent CSRF on state-mutating endpoints.
</Warning>

| Cookie | HttpOnly | Path | Flags |
|---|---|---|---|
| `access_token` | ✅ | `/` | Secure (prod), SameSite |
| `refresh_token` | ✅ | `/api/v1/auth/refresh` | Secure (prod), SameSite |
| `pre_auth_token` | ✅ | `/api/v1/auth/2fa/verify` | Secure (prod), SameSite |

## Google OAuth2 Flow

Auth Backend implements the Authorization Code flow via Spring Security's OAuth2 Login support. The authorization request state is stored in a cookie (`HttpCookieOAuth2AuthorizationRequestRepository`) rather than in the HTTP session, keeping the server fully stateless.

<Steps>
  <Step title="Initiate the flow">
    Redirect the user's browser to `/oauth2/authorization/google`. Spring Security builds the Google authorization URL and saves the OAuth2 state in a short-lived cookie.
  </Step>
  <Step title="Google authenticates the user">
    The user is redirected to Google's consent screen. After approval, Google redirects back to `/login/oauth2/code/google` with an authorization code.
  </Step>
  <Step title="OAuth2SuccessHandler runs">
    The success handler extracts the user's email, name, and avatar from Google's user-info endpoint and follows one of three paths:

    - **Returning OAuth2 user** — an account already linked to the same Google `sub` ID exists. Profile fields (name, avatar) are synced if they changed.
    - **New user** — no matching account found. A new `User` is created with `emailVerified=true`, `active=true`, `provider="google"`, and no password.
    - **Email conflict** — the email is already registered as a local (password) account. The flow redirects to the frontend with `?error=EMAIL_EXISTS_WITH_PASSWORD`.
  </Step>
  <Step title="Tokens issued (or 2FA required)">
    If the user does **not** have 2FA enabled, `access_token` and `refresh_token` cookies are written and the browser is redirected to `app.oauth2.redirect-uri.success`. If 2FA is enabled, a `pre_auth_token` cookie is written instead and the browser is redirected to `app.oauth2.redirect-uri.two-factor` (default: `http://localhost:4200/auth/verify-2fa`).
  </Step>
</Steps>

<Info>
  OAuth2 users never have a password field set. They cannot use the local login endpoint or the forgot-password flow.
</Info>

## Local vs. OAuth2 Accounts

<Tabs>
  <Tab title="Local Account">
    - Registered via `POST /api/v1/auth/register`
    - Password hashed with **BCrypt cost 12**
    - `emailVerified` starts as `false` — the account **cannot log in** until a 6-digit OTP sent to the email address is submitted to `POST /api/v1/auth/verify-email`
    - Supports forgot-password / OTP reset flow
    - Can optionally enable TOTP 2FA after login
  </Tab>
  <Tab title="OAuth2 (Google) Account">
    - Created automatically on first Google login
    - No password stored (`password` field is `null`)
    - `emailVerified` is set to `true` immediately because Google has already verified the address
    - Cannot use the local login endpoint
    - Can optionally enable TOTP 2FA after login
  </Tab>
</Tabs>

## Password Hashing

Local account passwords are hashed with **BCrypt at cost factor 12** using Spring Security's `BCryptPasswordEncoder`. The hash is stored in the `password` column of the `users` table and is never returned by any API endpoint.

```java SecurityConfig.java (excerpt)
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);
}
```

## CORS and Security Headers

CORS is configured in `SecurityConfig` to allow credentialed cross-origin requests from the default frontend origins. The `Access-Control-Allow-Credentials: true` header is required for HttpOnly cookie delivery in the browser.

```java SecurityConfig.java (excerpt)
config.setAllowedOrigins(List.of("http://localhost:3000", "http://localhost:4200"));
config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE"));
config.setAllowedHeaders(List.of("*"));
config.setAllowCredentials(true);
config.setMaxAge(3600L);
```

<Warning>
  Replace `localhost:3000` and `localhost:4200` with your production frontend domain before deploying. Leaving these values as-is allows any browser running on `localhost` to make credentialed requests to your production API.
</Warning>

Spring Security's CSRF protection is disabled (`AbstractHttpConfigurer::disable`) because the API is stateless and uses short-lived JWTs rather than cookie-session-based authentication. All state-mutating requests require a valid JWT or are scoped to short-lived cookies that cannot be forged cross-origin with CSRF.
