Auth Backend ships with development-friendly defaults that prioritise convenience over security. Before exposing the service to real users, you must review and tighten every item on this page. Each section maps to a concrete change in `application.properties`, `SecurityConfig.java`, or your infrastructure, and includes the exact property name or code reference so nothing is ambiguous.

<Warning>
  Running Auth Backend in production with the development defaults — insecure cookies, `localhost` CORS origins, a placeholder JWT secret, and no Redis TLS — constitutes a critical security misconfiguration. Work through every item below before going live.
</Warning>

---

## Hardening Checklist

<Steps>
  <Step title="Secure cookies">
    The application sets an `access_token` and a `refresh_token` as `HttpOnly` cookies. In development they are sent over plain HTTP (`app.cookie.secure=false`). In production, cookies must be restricted to HTTPS-only connections and tightened against CSRF via the `SameSite` policy.

    ```properties application-prod.properties
    app.cookie.secure=true
    app.cookie.same-site=Strict
    ```

    `SameSite=Strict` means the browser will not send cookies on any cross-site request, including top-level navigations from other origins. If your frontend and API share the same registrable domain this is the safest setting. Use `Lax` only if you have a legitimate cross-site navigation flow that requires cookie transmission.

    <Note>
      `app.cookie.secure=true` requires the API to be served over HTTPS. If you terminate TLS at a load balancer or reverse proxy, ensure the proxy forwards the original scheme correctly.
    </Note>
  </Step>

  <Step title="Use a strong JWT secret">
    The development placeholder (`clave_de_desarrollo_reemplazar_en_produccion_32chars_min`) must be replaced before deployment. The JWT library (jjwt 0.12.6) requires the HMAC-SHA secret to be at least 256 bits (32 bytes) for HS256.

    Generate a strong secret:
    ```bash generate-jwt-secret.sh
    openssl rand -base64 48
    ```

    Set it via an environment variable injected at startup — never hard-code it in a committed properties file:
    ```properties application-prod.properties
    jwt.secret=${JWT_SECRET}
    jwt.time.expiration=900000
    jwt.time.refresh-expiration=604800000
    ```

    Store `JWT_SECRET` in your secrets manager (AWS Secrets Manager, HashiCorp Vault, Kubernetes Secret, etc.) and inject it as an environment variable at container or process start.
  </Step>

  <Step title="Restrict CORS to your production domain">
    `SecurityConfig.java` currently allows `http://localhost:3000` and `http://localhost:4200` as CORS origins:

    ```java SecurityConfig.java (development)
    config.setAllowedOrigins(List.of("http://localhost:3000", "http://localhost:4200"));
    ```

    In production you must replace that list with your actual frontend domain. The comment in the source file confirms this: `// reemplazar en prod por la url de frontend`.

    Update `SecurityConfig.java` to read the allowed origins from an environment variable or a profile-specific property, for example:

    ```java SecurityConfig.java (production pattern)
    config.setAllowedOrigins(List.of("https://app.yourdomain.com"));
    ```

    <Warning>
      Never use `*` (wildcard) for `allowedOrigins` when `allowCredentials` is `true`. Spring Security will reject that configuration, and for good reason — it would allow any site to make credentialed requests to your API.
    </Warning>
  </Step>

  <Step title="Enable Redis TLS and authentication">
    The development compose stack runs Redis without a password or TLS. In production, connect to a secured Redis instance. The commented-out lines in `application.properties` show exactly what to set:

    ```properties application-prod.properties
    spring.data.redis.host=${REDIS_HOST}
    spring.data.redis.port=${REDIS_PORT}
    spring.data.redis.password=${REDIS_PASSWORD}
    spring.data.redis.ssl.enabled=true
    spring.data.redis.connect-timeout=2s
    spring.data.redis.timeout=2s
    ```

    If you are using a managed Redis service (ElastiCache, Redis Cloud, Upstash), use the TLS endpoint hostname it provides and the access credentials from your service console.
  </Step>

  <Step title="Rotate the AES encryption key">
    `app.encryption.secret-key` is a 32-byte Base64-encoded AES-256 key used to encrypt TOTP secrets and 2FA backup codes before they are written to the database. Every deployment must have its own unique key.

    Generate a key:
    ```bash generate-aes-key.sh
    openssl rand -base64 32
    ```

    ```properties application-prod.properties
    app.encryption.secret-key=${ENCRYPTION_SECRET_KEY}
    ```

    <Warning>
      This key cannot be changed after users have enrolled in 2FA without running a migration that decrypts existing ciphertext and re-encrypts it with the new key. Treat it as a long-lived, highly sensitive credential and back it up securely.
    </Warning>
  </Step>

  <Step title="Register the production OAuth2 callback URL">
    The Google OAuth2 redirect URI must be registered in [Google Cloud Console](https://console.cloud.google.com/) under **APIs & Services → Credentials → Authorised redirect URIs**.

    For production, add:
    ```
    https://yourdomain.com/login/oauth2/code/google
    ```

    Then set the corresponding Spring properties (via environment variable or secrets manager):

    ```properties application-prod.properties
    spring.security.oauth2.client.registration.google.client-id=${GOOGLE_CLIENT_ID}
    spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
    spring.security.oauth2.client.registration.google.scope=openid,email,profile
    ```

    Update the OAuth2 redirect targets as well:
    ```properties application-prod.properties
    # Set these via environment variables
    # OAUTH2_REDIRECT_SUCCESS=https://app.yourdomain.com/auth/callback
    # OAUTH2_REDIRECT_FAILURE=https://app.yourdomain.com/login
    ```

    <Info>
      The development callback URL (`http://localhost:8080/login/oauth2/code/google`) can remain registered in Google Cloud Console for local testing as long as the production URL is also listed.
    </Info>
  </Step>

  <Step title="Use a production-grade PostgreSQL instance">
    The development configuration targets `localhost:5432` with placeholder credentials. In production:

    - Use a managed PostgreSQL 17 service (RDS, Cloud SQL, Supabase, etc.) or a dedicated server.
    - Use a non-default port if possible.
    - Use strong, randomly generated credentials.
    - Change `spring.jpa.hibernate.ddl-auto` from `update` to `validate`. `update` mutates your schema on startup — appropriate for development, dangerous in production if a migration goes wrong.
    - Disable SQL logging to avoid leaking query structures to log aggregators.

    ```properties application-prod.properties
    spring.datasource.url=jdbc:postgresql://${POSTGRES_HOST}:${POSTGRES_PORT}/${POSTGRES_DB}
    spring.datasource.username=${POSTGRES_USER}
    spring.datasource.password=${POSTGRES_PASSWORD}

    spring.jpa.hibernate.ddl-auto=validate
    spring.jpa.show-sql=false
    spring.jpa.properties.hibernate.format_sql=false
    spring.jpa.properties.highlight_sql=false
    spring.jpa.open-in-view=false
    ```
  </Step>

  <Step title="Never commit secrets to source control">
    Auth Backend already externalises all sensitive values through `${VAR}` placeholders, which is the right pattern. Enforce it operationally:

    - Add `.env` and any `application-local.properties` files to `.gitignore`.
    - Use a secret scanning tool (e.g. `git-secrets`, `truffleHog`, or GitHub's secret scanning) in your CI pipeline.
    - Inject secrets at runtime via your platform's secret injection mechanism (environment variables, mounted volumes from a vault, etc.).
    - Rotate secrets on a schedule and immediately after any suspected exposure.
  </Step>

  <Step title="Reduce application log verbosity">
    The default `application.properties` sets `logging.level.com.vc.auth_backend=INFO`, which can include sensitive request details. In production, raise the threshold and ship logs to a centralised system (Datadog, Grafana Loki, AWS CloudWatch, etc.) with access controls.

    ```properties application-prod.properties
    logging.level.com.vc.auth_backend=WARN
    logging.level.org.springframework.security=WARN
    logging.level.org.hibernate.SQL=WARN
    ```

    <Tip>
      Use structured JSON logging (e.g. via Logback's `JsonEncoder`) so your log aggregator can index fields like `traceId`, `userId`, and HTTP status codes without regex parsing.
    </Tip>
  </Step>

  <Step title="Confirm virtual threads are enabled">
    `application.properties` already sets `spring.threads.virtual.enabled=true`, which enables Java 21+ virtual threads for Spring MVC's request handling. This improves throughput under high concurrency at no additional cost. Verify your production JVM is Java 21 or later (the project targets Java 25 per `build.gradle.kts`).

    ```bash verify-java.sh
    java --version
    # Expected: openjdk 25 ...
    ```

    ```properties application-prod.properties
    # Already set — confirm it is not overridden in your prod config
    spring.threads.virtual.enabled=true
    ```
  </Step>
</Steps>

## Sample `application-prod.properties`

The snippet below consolidates all the hardening changes above into a single profile-specific file. Activate it with `--spring.profiles.active=prod` or `SPRING_PROFILES_ACTIVE=prod`.

<Info>
  All `${...}` placeholders must be satisfied by environment variables or a secrets manager before the application starts. The application will fail to start if any required placeholder is unresolved.
</Info>

```properties application-prod.properties
# ─── Application profile ──────────────────────────────────────────────────────
spring.application.name=auth
spring.profiles.active=prod

# ─── Database ─────────────────────────────────────────────────────────────────
spring.datasource.url=jdbc:postgresql://${POSTGRES_HOST}:${POSTGRES_PORT}/${POSTGRES_DB}
spring.datasource.username=${POSTGRES_USER}
spring.datasource.password=${POSTGRES_PASSWORD}

spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=false
spring.jpa.properties.hibernate.format_sql=false
spring.jpa.properties.highlight_sql=false
spring.jpa.open-in-view=false

# ─── Virtual threads ──────────────────────────────────────────────────────────
spring.threads.virtual.enabled=true

# ─── JWT ──────────────────────────────────────────────────────────────────────
jwt.secret=${JWT_SECRET}
jwt.time.expiration=900000
jwt.time.refresh-expiration=604800000

# ─── Cookies ──────────────────────────────────────────────────────────────────
app.cookie.secure=true
app.cookie.same-site=Strict

# ─── Redis ────────────────────────────────────────────────────────────────────
spring.data.redis.host=${REDIS_HOST}
spring.data.redis.port=${REDIS_PORT}
spring.data.redis.password=${REDIS_PASSWORD}
spring.data.redis.ssl.enabled=true
spring.data.redis.connect-timeout=2s
spring.data.redis.timeout=2s

# ─── Cloudinary ───────────────────────────────────────────────────────────────
cloudinary.cloud-name=${CLOUDINARY_CLOUD_NAME}
cloudinary.api-key=${CLOUDINARY_API_KEY}
cloudinary.api-secret=${CLOUDINARY_API_SECRET}

# ─── Email (Resend) ───────────────────────────────────────────────────────────
app.email.from=${EMAIL_FROM}
resend.api-key=${RESEND_API_KEY}
app.otp.expiration-minutes=${OTP_EXPIRATION_MINUTES}
app.email-verification.expiration-minutes=15

# ─── Encryption ───────────────────────────────────────────────────────────────
app.encryption.secret-key=${ENCRYPTION_SECRET_KEY}

# ─── 2FA ──────────────────────────────────────────────────────────────────────
app.2fa.pre-auth-expiration-minutes=5
app.2fa.issuer=YourAppName
app.2fa.digits=6
app.2fa.period=30

# ─── Google OAuth2 ────────────────────────────────────────────────────────────
spring.security.oauth2.client.registration.google.client-id=${GOOGLE_CLIENT_ID}
spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
spring.security.oauth2.client.registration.google.scope=openid,email,profile

# ─── OAuth2 redirect targets ──────────────────────────────────────────────────
# Consumed by OAuth2SuccessHandler / OAuth2FailureHandler
# OAUTH2_REDIRECT_SUCCESS and OAUTH2_REDIRECT_FAILURE must be set as env vars

# ─── File upload limits ───────────────────────────────────────────────────────
spring.servlet.multipart.max-file-size=5MB
spring.servlet.multipart.max-request-size=10MB

# ─── Logging ──────────────────────────────────────────────────────────────────
logging.level.com.vc.auth_backend=WARN
logging.level.org.springframework.security=WARN
logging.level.org.hibernate.SQL=WARN

# ─── Problem detail ───────────────────────────────────────────────────────────
spring.mvc.problemdetails.enabled=true
```

    `app.cookie.secure=true` and `app.cookie.same-site=Strict` must be set before going live.
  </Card>

    Minimum 32 characters, randomly generated, stored in a secrets manager, never committed.

  </Card>

  </Card>

  </Card>
</CardGroup>
